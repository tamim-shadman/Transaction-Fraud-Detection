## 1. Executive Summary

This report establishes the storage governance, capacity profiling, and safe cleanup architecture for the **Transaction Fraud Detection Analytics Platform**.

Uncontrolled growth in analytical repositories typically occurs across five primary vectors: transient staging directories (`.staging/`), unpruned backup archives (`backups/`), Python and Node bytecode caches (`__pycache__`, `.tsbuildinfo`), redundant duplicate derived JSON stores, and abandoned temporary browser exports.

Phase 7 implements an automated storage profiling and cleanup utility (`scripts/storage_manager.py`) equipped with:
1. **Directory-Level Capacity Profiling**: Measures exact file counts, byte sizes, and persistence classifications.
2. **Explicit Retention Policies**: Configurable caps for backup counts (`MAX_BACKUP_COUNT=10`) and storage limits (`STORAGE_LIMIT_MB=500`).
3. **Hardened Safety Guards**: Strict enforcement that prevents cleanup from touching canonical tables (`tables/`), figures (`figures/`), notebooks, or historical snapshots (`snapshots/`).
4. **Interactive Dry-Run Mode**: Allows operators to preview every candidate file, byte size, and deletion reason prior to destruction.

## 3. Growth Vectors & Mitigation Controls

### 3.1 Growth Vector 1: Backup Archive Accumulation
- **Risk**: Creating backups prior to every deployment, release, and data refresh could consume hundreds of megabytes over time.
- **Mitigation Control**: `scripts/backup_manager.py` implements automated FIFO retention:
  ```python
  def prune_old_backups(max_count: int = 10):
      archives = sorted(BACKUPS_DIR.glob("backup_*.zip"), key=lambda p: p.stat().st_mtime)
      if len(archives) > max_count:
          for p in archives[: len(archives) - max_count]:
              p.unlink()
  ```
  Archives beyond the 10 most recent are pruned automatically upon new backup creation.

### 3.2 Growth Vector 2: Ephemeral Pipeline Staging (`.staging/`)
- **Risk**: If the 6-stage data refresh pipeline in `analytics/refresh_engine.py` terminates unexpectedly during a schema validation assertion, staging files could remain in `app/public/data/.staging/`.
- **Mitigation Control**: `scripts/storage_manager.py` audits `.staging/` and removes abandoned staging directories during safe cleanup sweeps.

### 3.3 Growth Vector 3: Duplicate Derived Artifacts
- **Policy Invariant**: The static web data store (`app/public/data/tables/*.json`) does not duplicate the full raw transaction logs. It holds aggregated summary tables derived from the 46 CSV tables, capping client data delivery at ~3.5 MB uncompressed.

## 4. Safe Cleanup Architecture & Invariants

```mermaid
graph TD
    A[Trigger: scripts/storage_manager.py --action cleanup] --> B[Discover Cleanup Candidates]
    B --> C{Any Candidate in Protected Path?}
    C -- YES --> D[CRITICAL ERROR: Abort Operation]
    C -- NO --> E{Dry Run Mode?}
    E -- YES --> F[Output Candidate Manifest & Size Summary]
    E -- NO (--force) --> G[Safely Delete Ephemeral Targets & Bytecode]
```

### Safety Invariants Enforced in Code:
1. **Invariant 1 (Zero Source Mutation)**: `tables/`, `figures/`, `logs/`, `fraud_eda_colab(1).ipynb`, and `snapshots/` are registered in `PROTECTED_PATHS`. Any deletion attempt targeting these paths throws a fatal `RuntimeError`.
2. **Invariant 2 (Mandatory Confirmation)**: Destructive cleanup requires the explicit `--force` CLI flag. Without `--force`, the utility executes in non-destructive dry-run mode, printing every candidate file, path, and size.
